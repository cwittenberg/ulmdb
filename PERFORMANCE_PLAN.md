Acceptance rules:

1. Any oracle, recovery, durability, capacity or snapshot failure rejects the
   candidate immediately, regardless of speed.
2. Inspect every individual throughput, latency and lifecycle result. Negative
   point estimates remain visible. Never summarize regression away with a win
   count or an average over unrelated cases.
3. Initial four/three-process results are screening evidence. Use process-level
   paired ratios and uncertainty; individual queries are not independent
   experimental replicates. The existing sampled write p99 uses only eight
   samples per trial and cannot establish a production tail percentile.
4. A material repeatable slowdown beyond measured machine variability blocks
   acceptance. Marginal reductions around the user's clarified 2% example are
   reported alongside the gain and assessed after independent repeats. An
   unresolved adverse result is **inconclusive**, not a pass. Predeclare a
   fixed follow-up paired campaign when resolving noise, retain both campaigns,
   and do not repeatedly rerun until a favorable answer appears.
5. Set noise envelopes from baseline-versus-baseline runs before using them.
   They quantify uncertainty, not permission to consume a regression budget.
   A considerable regression in one cell can never be traded for another win;
   the user explicitly permits evaluating a marginal reduction against a large
   improvement after repeated full measurement.
6. Failed experiments are reverted with ownership-scoped edits. Restore the
   last accepted implementation and retain the failed evidence and explanation.

Final performance target: ULMDB beats contemporaneous local LMDB in every
throughput/latency/load/reopen cell for which an equivalent measurement exists,
with no considerable regression against starting ULMDB. Resource costs remain
visible and may not worsen materially without resolving the cause. Any unmet
target or unmeasured behavior is explicitly reported.

## 3. Profile and confirm the expensive mechanisms

Profiles are separate runs; their distorted timings are not benchmark results.

1. Check whether hardware/software perf events are allowed. If sampling is
   unavailable, record the restriction and use syscall tracing plus bounded
   phase instrumentation or another available profiler. Do not invent a CPU
   breakdown from source inspection.
2. Trace RAM single-write and disk single-write commits: syscall counts, bytes,
   time in witness validation, WAL emission, data fence, witness emission and
   witness fence. Compare LMDB under the same conditions. Preserve both
   acknowledged durability and tamper/corruption detection.
3. Profile sorted million-key loading and shuffled updates separately: search,
   leaf validation, copying, page splitting, allocation, catalog edits, freeze,
   redo construction/checksum, publication and automatic collection.
4. Quantify 4KiB copies, bytes validated/re-encoded per inserted record, page
   ownership transitions and time per transaction versus per record. Check
   scaling at several key counts without changing qualification workloads.
5. Profile reopen separately: WAL scan/decode, replay, historical retirement
   audit, selected-graph audit and owner/index rebuilding; measure history
   length versus live data. Do not skip audits to improve a number.
6. Confirm a mechanism with a controlled experiment and a quantified upper
   bound on its possible benefit. Source evidence identifies where to measure;
   it does not by itself establish the dominant cause.

Each profile receipt records command, binary/source identity, workload, storage,
tool overhead, observations, interpretation and the next decision it supports.

## 4. Architecture decisions follow the profiles

Keep immutable reader-facing B+tree and radix pages as the initial architectural
anchor. Allow a different writer/storage representation where evidence supports
it. Select a path by real state, ownership and storage properties, never by a
benchmark name or a fixture's keys. Ordinary API calls must benefit.

These are **candidate experiments, not established explanations**:

### A. Transaction-private page builder plus immutable serving pages

If page validation/copying dominates load, add an ownership-checked writer edit
or splice primitive. Shared pages copy once into private pages; subsequent
inserts edit bounded row/header regions. Preserve the existing persisted and
read formats, split rules, zero-tail rules and full fallback for other stores.
An exact-identity/revision validation certificate is considered only if repeated
validation is itself measured as material; it must preserve corruption rejection
and establish why each later mutation maintains the validated invariants.

This hybrid aims to give sorted and ordinary inserts a mutable construction
path while readers retain the already-fast immutable layout. Include random
inserts, replacements, variable-width transitions, deletes, aborts, pinned
snapshots and replay in differential tests.

### B. Storage-aware durable publication with unchanged semantics

If fixed publication work dominates RAM writes, examine equivalent ways to
validate witnesses/capacity, encode publication records and issue I/O. A mapped
or coalesced validation path is eligible only if it detects the live tampering
and truncation that existing APIs/tests reject. Keep ordered durability fences,
unknown-outcome poisoning, source lifetime and cross-database atomicity.

If a distinct protocol is warranted, specify a versioned recovery state machine
before implementing it. Compare a page-published path, compact WAL path and
size-aware hybrid using actual profiles. Never make tmpfs faster by quietly
turning durability off, and do not trade disk write performance for RAM speed.

### C. Checkpointed serving image plus bounded verified tail

If history replay dominates reopening, investigate an authenticated/checked
immutable checkpoint and a bounded redo tail. Specify atomic selection,
interrupted checkpoint publication, previous-generation fallback, retained
readers, corruption rejection, capacity accounting and continued writes first.
Evaluate existing hybrid/checkpoint components for reuse before adding a second
independent storage engine. No shortcut may trust an unaudited checkpoint or
change the meaning of an acknowledged commit.

For each option, write a decision record with measured attribution, expected
maximum gain, required invariants, rejected alternatives and falsification
criteria. Choose the smallest coherent change supported by the measurements.

## 5. One-change iteration loop

Each numbered iteration has the following retained receipt:

1. **Measure:** full previous results and a focused profile identify the cost.
2. **Strategize:** choose an architectural change that addresses that cost;
   estimate benefit and identify all possible affected paths.
3. **Confirm:** isolate the mechanism with a controlled experiment; reject the
   approach if the evidence does not support it.
4. **Implement:** one coherent change, with safe fallback and bounded resource
   behavior. Add tests for new invariants rather than tests mirroring helpers.
5. **Correctness:** targeted differential, boundary, snapshot and recovery
   tests; expand to the entire workspace and exact benchmark feature set.
6. **Benchmark:** rerun both complete suites and required paired baseline runs.
   Preserve every adverse cell and compare against initial and last accepted.
7. **Decide:** accept only after all regression gates pass; otherwise investigate
   a predeclared noise-resolution campaign, revise, or revert. Any source change
   starts a new implementation iteration and requires the full benchmark again.
8. **Update:** record evidence, change, exact result, residual bottleneck and
   next measurement. Reprofile after improvement because the bottleneck moves.

Do not stack several unmeasured changes or retain a failed fast path merely
because another change might eventually compensate for it.

## 6. Correctness and integration qualification

Run workspace tests and the exact nine-feature Resident benchmark configuration.
The Resident tests include ordinary writes, CompactV2/borrowed encoding,
corruption, private-index ownership, single-pass auditing and million-key pool
capacity. Storage tests cover direct/fused patches, directory sharing, rollback,
generation checks and quota admission.

For journal/publication/checkpoint changes, run fault-injection suites covering
append, data sync, witness sync, acknowledgment, returned EIO and abrupt process
exit on real storage and tmpfs. Recovery must reject corruption before mutating
the evidence. Old borrowed values and their addresses must remain valid through
concurrent publication and collection. No-op/abort sequence semantics remain.

Keep unsupported features and fixed capacities explicit. Resident currently
differs from Legacy, has bounded WAL/pools/recovery budgets and does not support
all public client functionality. A benchmark improvement does not authorize
silently switching public APIs or claiming LMDB-wide compatibility.
